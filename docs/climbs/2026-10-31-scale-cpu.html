Outcome

CPU the hub and Postgres spend to push, link, and read an estate of 115,545 entities through the API went from 200,213 ms to 71,780 ms: +64.1% (better). The noise floor was 10.86%, so only changes beyond it were kept.

The held-out score, which the agent never climbed against, went from 134,747 ms to 35,796 ms (+73.4%).

The guard tests passed on the final state.

What changed and why it is better

Pass 2 on the same estate of 115,535 entities, scored on the CPU the hub and Postgres spend, because other work on the machine made wall time swing by a third.

  • A batch’s relations are looked up by entity, and the source is matched in code. The query used to ask for one source’s relations. When Postgres’s statistics were stale, as they are while a fresh table fills, it walked every relation the source ever wrote, once per entity in the batch: 7.6 s for one lookup, 15 ms now. This is why the first push swung from 5 s to 54 s.
  • A rule that matches on a stored value reads stored values alone. It used to build both blueprints whole, derived fields and status included, and again after every rule that changed links. Re-linking after the second push fell from 21 s to under 1 s.
  • An entity’s page and a walk copy what a blueprint already keeps. They used to derive the entity and everything its derived fields read. A page fell from about 330 ms to 24 ms, a two-hop walk from 900 ms to 13 ms.
  • A blueprint’s build borrows what other blueprints keep. Deriving one blueprint loads the neighbours its derived fields read, and theirs. Now a neighbour another blueprint already keeps stands in, and the blueprints others read are built first. The summary and search halved. A walk inside a re-link still reads afresh.
  • Inheritance says what it changed as it changes it. It used to say so once at the end of a pass, and named only blueprints it had never changed before, so a second change to one blueprint refreshed nothing.

Tried and not kept:

  • Writing a rule’s links in one statement each way: linking after the first push halved, but the rest of the run moved more than it saved.
  • Cheaper derivation per entity (narrow relation reads, one source lookup per pass, no list copies): 4.3 % better, inside this pass’s noise floor of 10.9 %, which one slow baseline run set. It goes into the next pass.

What was measured

  • Score: BENCH_PG_CONTAINER=orrery-pg BENCH_SCALE=3 LOG_LEVEL=error node bench/scale.ts \| tail -1 \| node -e "const d = JSON.parse(require('fs').readFileSync(0, 'utf8')); console.log(JSON.stringify({ value: d.metrics['cpu.total'], metrics: d.metrics }))", run 3 times per attempt; the median counts.
  • Held-out: BENCH_PG_CONTAINER=orrery-pg BENCH_SCALE=1.5 LOG_LEVEL=error node bench/scale.ts \| tail -1 \| node -e "const d = JSON.parse(require('fs').readFileSync(0, 'utf8')); console.log(JSON.stringify({ value: d.metrics['cpu.total'], metrics: d.metrics }))", measured only at the start and the end.
  • Noise floor: 10.86% (spread across 3 baseline runs: 10.86%).
